# RoomSync

## What this project is

RoomSync is a capstone project: a **Real-Time Classroom Schedule Display and
Attendance Monitoring System**. The final deployment target is a
**Raspberry Pi 4** mounted beside a classroom door, wired to an **RC522 RFID
reader** and driving a **7-inch touchscreen**. Students and teachers tap an
RFID-enabled ID card to log attendance for whatever class is currently
scheduled in that room, and the screen shows:

- The current/next class schedule for that room.
- Live present/absent status as people tap in.
- An end-of-session attendance summary once a class period ends.

**The RC522 is now physically working on the Raspberry Pi 4** — confirmed
reading a card's unique ID via `mfrc522`'s `SimpleMFRC522().read_id()`.
`rfid_listener.py` (see "RFID hardware listener" below) is the real
reader pathway this project was originally built to swap in: it POSTs
each scanned tag ID to the exact same `/kiosk` endpoint and `rfid_tag`
form field the simulated kiosk page already used, so the rest of the app
needed no changes at all. Everything was originally built and tested on a
regular laptop first, and still can be — RFID taps can still be simulated
via `/kiosk`'s web page (a text input and quick-tap buttons) whenever the
Pi/reader/`rfid_listener.py` aren't running, e.g. for local dev on a
laptop. The 7-inch touchscreen kiosk-mode setup on the Pi itself is still
outstanding — see "Known simplifications" below.

## Tech stack

- **Backend:** Python 3, Flask (see `requirements.txt`). Also `pywebpush`
  for Web Push notifications and `requests` for both `rfid_listener.py`
  and SMS notifications (see "Web Push Notifications" and "SMS
  Notifications" below) — bonus features beyond the three core manuscript
  objectives, same category as the teacher dashboard and login system.
- **Database:** SQLite (`roomsync.db`), accessed via the standard `sqlite3`
  module — no ORM.
- **Frontend:** Server-rendered Jinja2 templates + plain CSS/JS (no frontend
  framework), styled as an Apple (visionOS-like) frosted-glass theme — see
  "Visual theme" under Conventions. One small vanilla-JS service worker
  (`static/sw.js`) for push notifications.

## Conventions

- **24-hour ("military") time everywhere.** Class times are stored as
  `HH:MM`, every page shows `HH:MM` (or `HH:MM:SS` for a tap timestamp),
  the display clock on `/` runs 24-hour, and every admin form picks a time
  with `time_input` in `_macros.html`: a field-shaped button that opens a
  **scroll-wheel picker** (hours 00–23, minutes 00–59; the user asked for
  scrolling instead of typing). Script in `base.html`, styles under
  `.time-picker` in `style.css`; the pick goes in a hidden input posting
  plain `HH:MM`. Deliberately *not* `<input type="time">`, which many
  browsers render 12-hour AM/PM depending on the OS locale. One mouse-wheel
  notch moves one number; the panel opens upward/right-aligned when it
  would run off-screen. Gotcha: hiding the panel resets the wheels' scroll
  to 0 and fires a scroll event — the script ignores scrolls while hidden,
  or the field would be overwritten with `00:00`. `normalize_time_24h()` in
  `app.py` still validates on the server (accepts loose forms like `8:00`,
  `0800`; anything else, e.g. `3:00 PM`, is rejected with a flash message). Never introduce a 12-hour
  time anywhere — this was a thesis-panel requirement. Use the
  `time_range` Jinja filter (`{{ c.start_time|time_range(c.end_time) }}`
  -> `08:00–09:30`, or "Not scheduled") to show a class's schedule.
- **One date format for display**: the `fmt_date` Jinja filter
  (`2026-11-03` -> `Tue, 03 Nov 2026`). Dates are still stored and passed
  in URLs as ISO `YYYY-MM-DD`.
- **Navigation**: the navbar in `base.html` is role-specific (each role
  only sees pages it can use) and highlights the current section via
  `request.endpoint`; every sub-page starts with `breadcrumbs(...)` from
  `_macros.html`. Flash messages are rendered once, in `base.html` (a page
  that wants them elsewhere overrides `{% block flashes %}`, like
  `login.html`) — don't add another `get_flashed_messages()` loop to a
  page, or messages will show twice.
- **Forms use visible labels** (`.form-grid` > `.field` > `<label>` +
  input), not placeholder-only inputs.
- **Keep the UI clean — no help text.** The user explicitly asked for
  explanatory paragraphs, tips, "e.g." placeholders, and "(24-hr)"-style
  label suffixes to be removed everywhere. Pages carry a heading, short
  labels, and short empty states ("No classes yet.") only; the door
  display keeps just the one-line prompts people need ("Tap your card").
- **Visual theme: Apple-style frosted glass** (the user's pick, modeled on
  visionOS). Translucent white panels (`--glass`, `--glass-border`) over a
  soft warm-gray gradient backdrop (`body::before`), big rounded corners
  (`--radius` 24px), pill-shaped buttons/inputs/chips, soft shadows, the
  system font stack (SF Pro on Apple devices, Segoe UI on Windows). The
  navbar is a floating glass bar; each stage on the door display sits on
  one large glass platter (`.display-root > div`). **RoomSync red
  (`--accent`) is kept, but only for main buttons (incl. Save), the active
  menu item / date chip, and highlights**; green/amber/blue/red still mark
  attendance status. Real blur (`backdrop-filter`) is used only on the
  sticky navbar and popups, where content actually passes behind them,
  to keep the Raspberry Pi display light to render. Use the `:root`
  tokens in `style.css` rather than new hard-coded colors. The active item
  in the navbar (`.navbar-links`) and in the date-range chips
  (`.chip-row`, Attendance Records and the student dashboard) has a
  **sliding red pill** (`.nav-indicator`, JS in `base.html`): clicking
  another link glides the pill over, then loads the page after ~0.3 s
  (skipped for reduced motion or modifier-clicks). A container with no
  `a.active` (e.g. a custom date range) gets no pill. Next to "RoomSync"
  in the navbar is a pulsing green "online" dot.
- **Lists are read-only rows with Edit/Delete.** Teachers/Students tables
  show plain text with an **Edit** button (-> that person's own page,
  where all editing happens) and a **Delete** button; no inline `<input>`s
  in table cells. Put row buttons in `<td class="cell-actions"><div
  class="row-actions">`. Long lists get a search box:
  `<input type="search" class="table-search" data-table="<table id>">`
  (filtering JS lives in `base.html`). Use `.btn-view` for a row's
  secondary action and `.btn-delete` (red text, no fill) for destructive
  ones; confirm dialogs name the thing being deleted, built with
  `|tojson` inside a single-quoted `onsubmit` so apostrophes in names
  can't break the JS.
- **Flash messages** have a × to close them; success messages also fade
  out after 6 s (JS in `base.html`).
- **Popups**: a `<dialog class="modal">` with `.modal-header` (title + ×),
  `.modal-body` (a `.form-grid`; `.field-full` for a full-width row), and
  `.modal-footer` (Cancel + primary button). Open it with any
  `<button data-open-dialog="<dialog id>">`; `data-close-dialog` on a
  button inside closes it (JS in `base.html`, which also closes on a
  background click). Put `autofocus` on the first input.

## Database schema

Eight tables, created by `database.py`:

1. **students** — `student_id` (PK), `rfid_tag` (unique), `first_name`,
   `last_name`, `section`, `username` (unique, nullable), `password_hash`
   (nullable), `phone_number` (nullable). A freshly added student isn't in
   any class — see **enrollments** below for how that's set up.
   `username`/`password_hash` are the student portal login
   (`/student-dashboard`), the same pattern as `teachers.username`/
   `password_hash` below — an admin sets them when adding or editing a
   student; a student never signs up or sets their own credentials, and
   both stay `NULL` (no portal access) until an admin does.
   `phone_number` is likewise admin-set and optional — where SMS
   notifications are sent (see "SMS Notifications" below); a student with
   no number set just never gets an SMS, the same as one with no push
   subscription never gets a push.
2. **teachers** — `teacher_id` (PK), `rfid_tag` (unique), `first_name`,
   `last_name`, `username` (unique, nullable), `password_hash` (nullable),
   `phone_number` (nullable). The login `username`/`password_hash` pair is
   set by an admin when the teacher is created (see "Login system" below)
   — a teacher never signs up or sets their own credentials.
   `phone_number` is the same nullable, admin-set, SMS-notification-target
   column as `students.phone_number` above.
3. **classes** — `class_id` (PK), `subject_name`, `teacher_id` (FK ->
   `teachers`, **nullable**), `room_number` (nullable), `start_time`
   (`HH:MM`, nullable), `end_time` (`HH:MM`, nullable),
   `attendance_window_minutes` (default 15). A class has **no day-of-week
   concept** — once `room_number`, `start_time`, and `end_time` are all
   set, the class is assumed to meet every single day at that time; there
   is no separate schedule table. "Add a Class" (see "Admin pages" below)
   only ever sets `subject_name` — `teacher_id`/`room_number`/`start_time`/
   `end_time` all start out `NULL` and stay that way — meaning the class
   has no teacher and isn't tappable yet — until a separate "Assign Class"
   step sets `teacher_id` and the schedule together (never independently:
   a class can't have a schedule without a teacher, or a teacher without a
   room/time — `admin_assign_class()` in `app.py` always sets both at
   once). `attendance_window_minutes` is used two ways by the display
   state machine: as the "how early is too early" cutoff before
   `start_time` for a teacher's tap, and as the length (in minutes) of the
   attendance countdown once a teacher opens the window.
4. **attendance** — `attendance_id` (PK), `student_id` (FK), `class_id` (FK),
   `date` (`YYYY-MM-DD`), `time_tapped` (`HH:MM:SS`), `status`
   (`present` / `late` / `absent`).
5. **admins** — `admin_id` (PK), `username` (unique), `password_hash`. A
   separate table from `teachers` rather than a role flag on one table,
   since admins have no RFID tag, no classes, and no other teacher-only
   columns.
6. **enrollments** — `enrollment_id` (PK), `student_id` (FK ->
   `students`), `class_id` (FK -> `classes`), `UNIQUE(student_id, class_id)`.
   The many-to-many link between students and classes — a student can be
   enrolled in several classes at once, and a class's attendance-taking
   (the live present/absent boxes on `/`, the present count, the
   perfect-attendance auto-close check, and every roster shown anywhere —
   `session_summary`, `/summary`, the teacher dashboard) is scoped to only
   the students enrolled in it here, not every student in the school. See
   "Admin pages" below for how enrollment is set up (pick a subject, then
   which schedule/teacher offering of it), and "How the attendance flow
   works" for how a non-enrolled student's tap is rejected. Enrolling is
   also rejected if the class's time overlaps one the student is already
   enrolled in (see `student_enrollment_conflict()` in `app.py`) — a
   student can't be in two classes at once, any more than a teacher can.
7. **rooms** — `room_id` (PK), `room_name` (unique). Just a catalog of room
   names, added via "Add a Room" — there's no "Assign Room" step; a room
   is put to use by picking it from the room dropdown in Assign Class (see
   "Admin pages" below). `classes.room_number` stores a plain copy of
   `room_name` rather than a foreign key (matching how `subject_name`/
   teacher names are also plain text elsewhere in `classes`), so deleting
   a room checks for any class currently using its name first rather than
   relying on a DB-level constraint.
8. **push_subscriptions** — `subscription_id` (PK), `user_type`
   (`'teacher'` or `'student'`), `user_id` (a `teacher_id` or `student_id`
   — which table it refers to depends on `user_type`, so there's no FK to
   either directly), `endpoint` (unique), `p256dh_key`, `auth_key`. One row
   per browser/device a teacher or student has granted notification
   permission on — a user can have several (e.g. a laptop and a phone).
   See "Web Push Notifications" below for the full picture.

Run `python database.py` any time to drop and recreate all tables with
fresh sample data (5 students each with a portal login, 3 teachers, 3
rooms, 3 classes already assigned to a teacher/room/time plus one
unassigned demo class, a handful of sample enrollments, a few sample
attendance rows, one sample admin account, and login credentials for each
sample teacher and student — the console output after running it prints
all the sample usernames/passwords). One student (Juan Dela Cruz) and one
teacher (Liza Fernandez) also get a sample `phone_number` (the same real
test number, for testing SMS end-to-end); everyone else's is left `NULL`
to demonstrate it's optional, same as `username`/`password_hash`.
`push_subscriptions` always starts empty (a browser has to actually
re-subscribe after any reset, since the old subscription rows are gone).
This is destructive to whatever is currently in `roomsync.db` — re-run
only when you want to reset to the demo dataset.

`python seed_history.py` adds history *without* resetting anything, so
the records pages have data to show. It adds 18 sample students with
realistic names (placeholder `SIM-00xx` RFID tags, no logins). It
enrolls *every* student in every scheduled class that doesn't overlap one
they're already in, using the same rule as
`student_enrollment_conflict()`, so back-to-back classes are a full block
schedule. It then writes weekday attendance from `SEMESTER_START`
(2026-08-17) to yesterday, skipping PH holidays and the odd cancelled
class. Each student keeps one habit profile across all their classes:
it's read from their existing history when they have some, otherwise a
random one (diligent / average / often late / often absent), with a few
more lates in classes before 08:30. Present taps fall inside the window
and late taps after it, and absence is no row. A student new to a class
that already has history gets a backfilled record for its past sessions,
so they don't show absent for all of them. History only ever extends
forward, never touches today, and leaves real taps alone, so re-running
adds nothing.

## How the attendance flow works (app.py)

The main display (`/`) is a polling-driven state machine (see `room_state`
in `app.py`), not a passive schedule board. It has one shared, in-memory
state for the room, updated by taps on `/kiosk` and read by the display via
`GET /api/display_state` (polled every ~2.5s). Stages:

- **welcome** — idle default, shows "WELCOME". Only teacher taps are
  accepted; a student tap here shows a brief rejection message (a "flash")
  and reverts to plain welcome once the flash expires.
- **teacher_early_confirm** — a teacher tapped within
  `attendance_window_minutes` before their class's `start_time` (e.g. a
  class starting at 11:15 with the default 15-minute window shows this
  stage for any teacher tap between 11:00 and 11:14). Shows a Yes/No
  prompt ("you are X minutes in advance..."). "No" resets to welcome;
  "Yes" moves to `teacher_early_wait`. A tap earlier than that window
  (before 11:00 in the example above) is disregarded entirely — no flash,
  no stage change, nothing shown on the shared display (the tapper still
  gets an inline message on `/kiosk` itself saying to try again closer to
  the window).
- **teacher_early_wait** — a teacher confirmed the early-tap prompt;
  waits for `start_time` itself to arrive (11:15 in the example above),
  showing a countdown ("Attendance starting in X minute(s)"), then
  auto-advances to `attendance_open` with no further action needed.
- **attendance_open** — a teacher confirmed and the wait ended, or a
  teacher tapped at/after `start_time` directly. A countdown starts,
  lasting `attendance_window_minutes`. Students *enrolled in this specific
  class* (see the `enrollments` table) can tap here to log `present`; a
  student who taps but isn't enrolled in it is rejected outright ("X is
  not enrolled in this class.") without writing to `attendance`, the same
  as any other invalid tap. Each accepted tap shows a brief flash
  confirmation (e.g. "Juan Dela Cruz - PRESENT") before reverting to the
  countdown view. Duplicate taps and taps while not in this stage are
  likewise rejected with their own flash message instead of writing to
  `attendance`. The live present count is shown as a row of boxes — one
  per *enrolled* student for this class, not every student in the school —
  that fill in green left-to-right in tap order as students check in,
  rather than each box being tied to a specific student. The moment every
  enrolled student has tapped in (`_attendance_is_perfect()` in `app.py`,
  which counts against `enrollments` for this `class_id`), the window closes
  early and moves straight to `class_ongoing`, without waiting out the
  rest of the countdown.
- **class_ongoing** — the countdown ended, or attendance was already
  perfect (`attendance_open` also closes at `end_time` itself, for a class
  shorter than its window). Shows "Class is Ongoing" prominently (with the
  subject and end time), the same roster boxes as `attendance_open` (green
  for on-time, amber for late), and a note that late arrivals may still
  tap in until `end_time` ("Attendance complete!" instead once everyone
  is in). **Late taps**: an enrolled student who hadn't tapped yet can
  still tap here and is recorded with status `late` (a thesis-panel
  requirement) — but only before the class's `end_time`;
  `handle_student_tap()` rejects any tap at/after `end_time` ("Class ended
  at HH:MM — attendance is closed."). A late tap returns `"success"` to
  the kiosk (positive beep) but flashes amber (`"warning"`) on the
  display. Once `end_time` passes, moves to `session_summary` instead of
  straight back to `welcome`. If the active class's teacher taps again
  here — before `end_time` — moves to `end_early_confirm` instead (see
  below).
- **end_early_confirm** — "End Class Early". Reached when the teacher whose
  class is currently active taps their RFID again during either
  `attendance_open` or `class_ongoing`, while the current time is still
  before that class's `end_time` (a *different* teacher's tap, a student's
  tap, or a same-teacher tap after `end_time` has already passed keep the
  normal "session already in progress" rejection — see
  `handle_teacher_tap()`). `room_state["early_end_origin"]` records which
  stage triggered it (`"attendance_open"` or `"class_ongoing"`) — this is
  what every "back out" exit throughout the whole early-end flow (this
  prompt's "No", and the `session_summary`/`session_summary_edit` "Cancel"
  buttons below) consults to decide where to land. Shows "Do you want to
  end the class early?" with a Yes/No prompt, handled by
  `/api/end_early_confirm`:
  - **No** — backs out with *nothing* changed: back to the live
    `attendance_open` countdown, exactly as it was, if that's where the
    request came from (there's no separate "window open" flag — the
    countdown was never touched while sitting in `end_early_confirm`, so
    resuming the stage just picks it back up), or back to `class_ongoing`
    if attendance was already closed when triggered (nothing to resume
    there). Either way attendance is left exactly as it was — the window
    is never closed or reopened by declining here.
  - **Yes** — sets `room_state["is_early_end"] = True` and moves to
    `session_summary` (`summary_expires_at` = now + 1 minute, rather than
    `end_time` + 1 minute since the class hasn't actually ended yet),
    reusing the same summary/edit flow described below.
    `early_end_origin` is deliberately *kept* (not cleared) here, since
    Cancel further down the flow still needs it.
- **session_summary** — a quick end-of-session recap: teacher, class name,
  and the list of present students, with a "Is this information correct?"
  Yes/No prompt — plus a third **Cancel** button, shown only when
  `is_early_end` is set. "Yes" locks the summary in (attendance rows are
  already correct, so nothing further is written) and returns to `welcome`
  — ending the class immediately even if `is_early_end` is set and the
  scheduled `end_time` hasn't arrived yet, since returning to `welcome`
  doesn't care what the original `end_time` was. A class ended early stays
  over for the rest of that day: `get_teacher_class_today()` skips any
  `(class_id, today)` in `_early_ended_sessions`, so the teacher tapping
  again before the old `end_time` gets their next class (or "No more
  classes scheduled today") instead of restarting this one — restarting
  would wipe that day's attendance, since `_open_attendance_window()`
  clears it when a session starts. Like `_early_ended_sessions` itself,
  this is in-memory and forgotten if the Flask process restarts. "No" moves to
  `session_summary_edit` to let the teacher correct who's actually
  present — the same for a normal end-of-session summary and one reached
  via an early-end request; `is_early_end` doesn't change what "No" does.
  "Cancel" (early-end only) backs all the way out, the same as answering
  "No" at `end_early_confirm` itself: it abandons the early-end attempt,
  clears `is_early_end` and `early_end_origin`, and returns to whichever
  stage `early_end_origin` names — the live `attendance_open` countdown
  (picking up exactly where it left off) if that's where the request came
  from, or `class_ongoing` if attendance was already closed. This stage
  (and `session_summary_edit`) is only available for 1 minute after it's
  entered (`summary_expires_at` = `end_time` + 1 minute normally, or now +
  1 minute for an early end) — if no button is pressed before that, it
  auto-confirms exactly like pressing "Yes" and returns to `welcome` (this
  applies even mid-early-end-attempt, since `advance_state()` doesn't
  distinguish `is_early_end` when checking the timeout).
- **session_summary_edit** — the same roster as `session_summary`, but each
  student is a tappable toggle (present ↔ absent). Tapping one calls
  `/api/session_summary_toggle`, which inserts or deletes that student's
  `attendance` row for the day (matching how a live tap during
  `attendance_open` records presence — there is no separate "corrected"
  flag). A "Confirm & Continue" button finalizes and returns to `welcome`
  (ending the class immediately if `is_early_end`); the same 1-minute
  `summary_expires_at` timeout applies here too. Also has its own
  **Cancel** button, shown only when `is_early_end` is set, with the exact
  same behavior as `session_summary`'s Cancel (back to `attendance_open`
  or `class_ongoing` per `early_end_origin`) — any toggles already made
  before cancelling stay written, since each one is committed immediately
  rather than staged.

All time-based transitions (window opening, countdown ending, class ending,
session-summary auto-confirm, flash expiry) are resolved lazily by
`advance_state()`, called at the start of every request that reads or
mutates `room_state` — there's no background scheduler/thread doing this
on a timer.

- `/kiosk` (GET shows the form, POST handles a simulated tap): looks up the
  tapped `rfid_tag` in `teachers` first, then `students`, and routes to
  `handle_teacher_tap()` / `handle_student_tap()` accordingly. Unknown tags
  just show an inline message on the kiosk page without touching the shared
  display state. `handle_student_tap()` accepts a student's tap during
  `attendance_open` (`present`) or `class_ongoing` before `end_time`
  (`late`), and additionally rejects a tap from a student who isn't
  enrolled (via `enrollments`) in the currently active `class_id`.
- `/api/teacher_confirm` (POST `{"action": "yes"|"no"}`) — handles the
  Yes/No buttons shown on the touchscreen during `teacher_early_confirm`.
- `/api/end_early_confirm` (POST `{"action": "yes"|"no"}`) — handles the
  Yes/No buttons during `end_early_confirm` (see above).
- `/api/session_summary_confirm` (POST `{"action": "yes"|"no"|"cancel"}`) —
  handles the Yes/No/Cancel buttons during `session_summary`, the "Confirm
  & Continue" button during `session_summary_edit` (sent as `"yes"`), and
  that same stage's own Cancel button (`"cancel"` is honored from either
  stage, but only when `is_early_end` is set, see above).
- `/api/session_summary_toggle` (POST `{"student_id": <id>}`) — flips one
  student's present/absent status while in `session_summary_edit`.
- `/summary` lets you pick a class and see present/late/absent counts and a
  full roster of that class's *enrolled* students (one with no attendance
  row that day shows as `absent`; a student not enrolled in the class
  doesn't appear, even if they have old attendance rows for it). Still
  time/schedule based, independent of the display state machine.
- `/api/status` is a small JSON endpoint (current class name, present count,
  total students), kept for backward compatibility — it reflects
  time-of-day schedule matching, not the `room_state` stage.
- `/admin` and `/admin/teachers/<id>` are the add/edit/delete management
  pages for `teachers`, `students`, and `classes` (see below).

## Login system

RoomSync has three login roles — **Teacher**, **Student**, and
**Administrator** — backed by Flask's session cookie, unrelated to the
`/kiosk` RFID-tap flow (a teacher's or student's *login* and their *RFID
tap* are two separate things; the tap flow still has no auth of its own,
see "Known simplifications").

- **`/login`** (`login()` in `app.py`) is a single page with a
  Teacher/Student/Admin toggle (`templates/login.html`); all three tabs
  post to the same route with a hidden `role` field, one of
  `LOGIN_ROLES = ("teacher", "admin", "student")`. On success it calls
  `session.clear()`, then sets `session["role"]` to that role and
  `session["user_id"]` to that user's `teacher_id`/`admin_id`/
  `student_id`, and redirects teachers to `/dashboard`, students to
  `/student-dashboard`, and admins to `/admin`. On failure it flashes
  "Invalid username or password" and re-renders the same tab. Passwords
  are checked with `werkzeug.security.check_password_hash` against the
  stored `password_hash` — plaintext passwords are never stored or
  compared directly.
- **`/logout`** clears the session and redirects to `/login`.
- **`login_required(role)`** (`app.py`) is a decorator factory —
  `@login_required(role="teacher")`, `@login_required(role="student")`, or
  `@login_required(role="admin")` — that redirects to `/login` unless
  `session["role"]` matches the required role and `session["user_id"]` is
  present. `/dashboard` is decorated with `role="teacher"`;
  `/student-dashboard` with `role="student"`; `/admin` and every one of
  its sub-routes (`/admin/teachers/*`, `/admin/students/*`,
  `/admin/rooms/*`, `/admin/classes/*`, add/assign/delete/reset-password
  alike) are decorated with `role="admin"`.
- The navbar (`base.html`) reads `session.get('role')` directly (Flask
  injects `session` into every template automatically) and shows a
  different link set per role: admin gets Home/Teachers/Students/Classes/
  Rooms/Reports/Today's Summary/Display/RFID Kiosk; a teacher gets My Dashboard/
  Attendance Records/Reports/Display; a student gets My Dashboard; logged out gets
  Display/RFID Kiosk/Today's Summary. The current section is highlighted.
  On the right it shows who's logged in — `session["display_name"]`, set
  by `login()` (the teacher's/student's full name, or the admin's
  username) — plus Logout (or Login).

### Teacher Dashboard (`/dashboard`)

Everything on this page is scoped to `session["user_id"]` — the logged-in
teacher only ever sees their own classes, never another teacher's.

- **Today's Sessions**: every one of this teacher's classes that has a
  room/time set (classes have no day-of-week concept — a class with a time
  set meets every day, so "today's sessions" is just that filter), each
  with a status badge ("Not started" / "In progress" / "Completed",
  normally derived from wall-clock time vs. `start_time`/`end_time` — but
  shown as "Completed" regardless of wall-clock time if `(class_id, today)`
  is in the in-memory `_early_ended_sessions` set, which is how the
  dashboard finds out a session was ended early through the End Class
  Early feature rather than by reaching its actual `end_time`; see
  `_reset_to_welcome()`, which records into it whenever a reset happens
  with `room_state["is_early_end"]` still set) and present/late/absent
  counts for today. The counts come from `get_roster_for_date()`, the same
  helper `/summary` uses for its own today-only roster — it was factored
  out of `summary()` specifically so both routes share one query instead of
  duplicating the present/late/absent roster logic. Each card links to
  that day's roster on Attendance Records.
- **My Classes** (Students / Records links per class) and **Message a
  Class** (SMS broadcast).

### Attendance Records (`/dashboard/attendance`) and date ranges

Past attendance has its own page (`dashboard_attendance()`), split off the
dashboard. Pick one of the teacher's classes (defaults to the first) and
a **date range** — a thesis-panel requirement: not just a single date or
a single month, but any From/To range, plus one-click presets (Today,
This Week, This Month, Last Month, Last 30 Days, All Time; default This
Month). Shows overall totals, every session held in the range (per-date
present/late/excused/absent, each with "View Roster"), and every enrolled
student's totals across the range (each with "Details" ->
`dashboard_student_attendance()`). `?date=` drills into one session's
full roster via `get_roster_for_date()`, where each status is editable
in place.

How ranges work (all in `app.py`, shared by every attendance page):
- `resolve_date_range(request.args, endpoint, **url_params)` reads
  `?range=<preset>` or `?range=custom&start=YYYY-MM-DD&end=YYYY-MM-DD`
  (reversed bounds are swapped; a blank side is unbounded; a custom pick
  that equals a preset shows as that preset) and returns the dict the
  `date_range_filter` macro renders, including `params` for links that
  should keep the same range.
- **Sessions-held rule**: there's no sessions table, so a date counts as
  a session for a class once *anyone* has an attendance row for it
  (`get_class_session_dates()`). On a session date, an enrolled student
  with no row is **absent** — the same rule `get_roster_for_date()` uses
  for one day. A date with no rows at all isn't a session, so nobody is
  counted absent for a day the class didn't meet.
  `get_class_attendance_report()` (per class) and
  `get_student_attendance_records()` (per student) both apply it. Known
  gap: there's no enrollment date, so a student enrolled mid-term shows
  absent for that class's earlier sessions.
- `dashboard_student_attendance()` (`/dashboard/classes/<cid>/students/
  <sid>`, replaces the old month-only view) lists every session of that
  class in the range with the student's status, each correctable.
- Corrections post to `dashboard_attendance_update()` with a hidden
  `next` (the page's own `request.full_path`); it only redirects to a
  plain local `/dashboard...` path (no scheme/host), so it can't be used
  as an open redirect.

### Student Report (`/admin/reports`, `/dashboard/reports`)

A panel recommendation: a user-defined report of one student's present /
late / excused / absent days. "Reports" in the admin and teacher navbars.
Both routes (`admin_student_report()`, `dashboard_student_report()`) build
the page with `_student_report()` in `app.py` and
`templates/student_report.html`. The viewer picks a student, one class or
all of them, a date range (same `date_range_filter` as Attendance Records,
default This Month), and which statuses to list (`?status=` checkboxes,
none ticked = all). The counts row always shows all four statuses; the
table lists only the ticked ones. Days come from
`get_student_attendance_records()`, so the sessions-held rule applies. An
admin can report on any student. A teacher can report only on students
enrolled in their own classes, and only for those classes. **Print**
uses the browser print dialog; `@media print` in `style.css` hides the
navbar/filters and shows a print header (`.print-only`).

### Student Dashboard (`/student-dashboard`)

The student-facing analogue of the teacher dashboard — same idea, scoped
to one student's own view instead of one teacher's. Everything here is
scoped to `session["user_id"]` — a student only ever sees their own
enrollments and attendance, never anyone else's.

- **My Classes**: every class in this student's `enrollments` (subject,
  teacher, room, schedule — "Not scheduled yet" for a class with no
  start/end time set, "Unassigned" for one with no teacher). Purely
  informational, no status badges or counts like the teacher's "Today's
  Sessions" — there's no live/completed distinction meaningful to a single
  student's own membership in a class.
- **My Attendance**: a class dropdown ("All my classes" or one enrolled
  class) plus the same date-range filter as the teacher's Attendance
  Records (default This Month). Shows totals and every session of those
  classes in the range with the student's own status, via
  `get_student_attendance_records()` — including **absent** for a
  session they missed (see the sessions-held rule above), so a missed
  day is visible to the student rather than silently left out.

## Admin pages (`/admin`, `/admin/teachers/<id>`, `/admin/students/<id>`)

`/admin` has four sections: **Teachers**, **Students**, **Rooms**, and
**Classes**. Teachers and Students are each a read-only table (with a
search box) where every row has **Edit** (-> that person's own page, where
all editing happens) and **Delete**. Adding someone is done in a **popup**:
the page header's "+ Add Teacher"/"+ Add Student" button opens a centered
`<dialog class="modal">` holding the add form (there's no add section on
the page itself), whose RFID tag comes from a **Scan Card** button (see
`_rfid_register.html`). The popup won't submit until a card is scanned,
and closing it (×, Cancel, Esc, or clicking the dimmed background)
cancels a scan that's still waiting.
"Add Student" takes a student's own info (`rfid_tag`/`first_name`/
`last_name`/`section`) plus a login `username`/`password` (both required,
same as "Add Teacher") — it creates the student record with no class
attached yet; enrolling them into one is a separate step from their Edit
page (see below). The Students table shows `username` read-only (like the
Teachers table does). A teacher's or student's username *is* editable
afterward, on their Edit page (the user asked for this; it was originally
immutable). The password is reset separately.

**Changing a username** (the Username field in the Details form on
`/admin/teachers/<id>` and `/admin/students/<id>`, saved by
`admin_update_teacher()`/`admin_update_student()`): it must be unique
within that table and contain no spaces (`_username_problem()` in
`app.py`), or the save is rejected with a flash and nothing is written.
Uniqueness ignores capital letters, as does `login()`, whose lookups use
`COLLATE NOCASE`, so `Angelica` logs in as `angelica`. Add Teacher/Add
Student run the same check (`_new_username_problem()`). A teacher and a
student may share one, since the login page picks the role first.
**An account with a username but no password can never log in**, and
`login()` refuses a NULL `password_hash`. That was a real bug with
`seed_history.py`'s sample students, which have neither. So the Details
form shows an extra **Password** field for any account with no
`password_hash`, and `_password_needed()` rejects a save that would leave
a username without a password. Leaving the field blank keeps the current username
(`COALESCE(?, username)`), so this form can never remove someone's login.
The old username stops working immediately. Sessions are keyed by
`user_id`, so anyone logged in stays logged in.

**Rooms** follows the same pattern as Classes below, just simpler — "Add a
Room" (`admin_add_room()`) is a single-field form (`room_name`) that just
adds the room to the catalog; there's deliberately no "Assign Room" step,
since a room is put to use by picking it from the room `<select>` inside
Assign Class instead (see below). The Rooms table just lists every room
name with a Delete button; `admin_delete_room()` blocks the delete (flash
error) while any class still has that `room_number`, mirroring how
deleting a teacher is blocked while they have a class assigned.

The Classes section is deliberately split into **two separate actions**,
matching the fact that a class's identity (its `subject_name`) and its
assignment (teacher + room + schedule) are set at different times by
different decisions:
- **Add a Class** (`admin_add_class()`) — a single-field form, just
  `subject_name`. Creates the class with `teacher_id` and the schedule
  left `NULL` — not assigned to anyone, not tappable yet (see "Database
  schema" above).
- **Assign Class** (`admin_assign_class()`, `POST /admin/classes/assign`)
  — a form picking an existing class from a dropdown (labeled with its
  current teacher/schedule if it has one, or "unassigned" if not), then a
  teacher, a room (a `<select>` populated from the `rooms` table, with a
  "No room yet" option — room stays optional, same as before Rooms
  existed, just picked rather than typed), start/end time, and attendance
  window, all set together in one update. `class_id` is a plain `<select>`
  inside the form rather than part of the URL, since the class being
  assigned is chosen at submit time.

  What happens on submit depends on whether the picked class's *current*
  `teacher_id` matches the *submitted* one:
  - **Same teacher** (including a fresh `NULL` -> some teacher first
    assignment) — updates that one class row in place. This is a plain
    reschedule/first-time assignment, same behavior as before.
  - **Different teacher** (the picked class already belongs to someone
    else, and a different teacher was submitted) — does **not** overwrite
    that row. Instead it `INSERT`s a *new* class row with the same
    `subject_name` and the submitted teacher/room/time, leaving the
    originally-picked class's assignment completely untouched. This is
    how two different teachers end up each teaching "the same class" (by
    `subject_name`) as separate sections, each with their own room and
    time — picking an already-assigned class in the dropdown is really
    "start from this subject," not "edit this exact row." The conflict
    checks below still run before either path (checked against every
    class, including the one that was picked from, in the new-section
    case — there's no `exclude_class_id` there since it isn't the same
    row being edited).

The Classes *table* itself (listing every class) is read-only — Subject,
Teacher (or an "Unassigned" pill), Room, Schedule, Window — with a
**Students** button (-> `admin_class_enroll`, the class's enrolled list
plus an enroll form) and **Delete** per row; all edits to
teacher/schedule go through Assign Class instead of inline table editing.

Each teacher's row has an "Edit" link to `/admin/teachers/<teacher_id>`
(`admin_teacher_detail` in `app.py`), which lists every class *already
assigned to that teacher* as a card — subject shown read-only, with room
(the same `<select>` from `rooms` as the main Assign Class form),
start/end time, and attendance window still editable inline (Save button)
for adjusting an existing assignment. Under the hood that Save button
posts to the same `admin_assign_class()` route as the main Assign Class
form, with `class_id` and `teacher_id` (fixed to this teacher) as hidden
fields — so assigning a *different* teacher to one of this teacher's
classes, or assigning a class to this teacher for the first time, still
has to go through the main Assign Class form on `/admin`. A class with no
start/end time yet shows a "Not scheduled" pill on its card until both
are set. The page's Details form has the teacher's RFID tag with a **Scan
Card** button beside it, which writes the next tap straight onto this
teacher (see `_rfid_register.html`).

Each student's row has an "Edit" link to `/admin/students/<student_id>`
(`admin_student_detail` in `app.py`), which has three parts:
- **Details** — the student's `rfid_tag` (with a **Scan Card** button, as
  on a teacher's page)/`first_name`/`last_name`/`section`/`username`/
  `phone_number`, the only place they're edited (submits to
  the same `admin_update_student()` route; a hidden `student_context`
  field, mirroring `teacher_context` for classes, is what tells it to
  redirect back to this page instead of `/admin`; see "Changing a
  username" above), plus a separate "Reset Password" mini-form
  (`admin_reset_student_password()`, `POST
  /admin/students/<id>/reset_password`) that sets a new password without
  needing the old one — the exact same pattern as
  `admin_reset_teacher_password()`.
- **Enrollment** — a table of the student's current enrollments (subject,
  teacher, room, schedule), each with an "Unenroll" button
  (`admin_unenroll_student()` — just deletes the `enrollments` row; their
  `attendance` history for that class is kept, so past records stay
  visible in date-specific views even after unenrolling), plus an "Enroll
  in a Class" form below it. That form is a two-step, JS-cascading pick:
  first a **Subject** dropdown (the distinct `subject_name`s among
  tappable classes — `start_time`/`end_time` both set — that this student
  isn't already enrolled in), then a **schedule** dropdown that fills in
  from a small inline `<script>` (filtering an embedded
  `enrollable_classes` JSON list by the chosen subject) showing that
  subject's specific offerings by teacher + time, since more than one
  teacher could teach sections of the same subject_name. Submitting posts
  the chosen `class_id` to `admin_enroll_student()`, which inserts into
  `enrollments` (flashing "Already enrolled in that class." on the
  `UNIQUE(student_id, class_id)` conflict, a message asking to pick a
  valid class if `class_id` doesn't resolve to a tappable class, or — via
  `student_enrollment_conflict()` — a message naming the already-enrolled
  class if the new one's time overlaps it).

**Time-conflict validation**: whenever a class's schedule is saved (from
either surface — both post to `admin_assign_class()` in `app.py`), two
independent checks run, each against every other class with a time set
(both scoped with `exclude_class_id` so a class never conflicts with its
own prior schedule when just being resaved):
- `class_time_conflict()` — checks it against every other class
  belonging to that *same teacher*. A teacher can't have two overlapping
  classes, since they'd need to be in two places at once, every day.
- `room_time_conflict()` — checks it against every other class in that
  *same room*, regardless of teacher. A room can't be double-booked at
  the same time every day, but two classes taught by *different* teachers
  in *different* rooms are completely fine sharing a time slot — there's
  no global "one class at a time" rule, only per-teacher and per-room.

Because every class recurs daily, any overlapping range on either axis is
a standing conflict, so the save is rejected with a flash error naming
the conflicting class (whichever check fired — teacher is checked first),
and nothing is written. `admin_enroll_student()` runs the analogous
per-student check, `student_enrollment_conflict()` — a student can't be
enrolled in two classes whose times overlap, the same logic applied to
the student's own enrolled-class schedule instead of a teacher's or a
room's.

Each entity/action has its own POST route or routes (`/admin/<entity>/add`,
`/admin/<entity>/<id>/update`, `/admin/<entity>/<id>/delete` for Teachers
and Students; Rooms only has `add`/`<id>/delete`, no update, since a room
is just a name; Classes has `add`/`<id>/delete` plus the shared `assign`
route in place of a per-class update), following a plain POST-redirect-GET
pattern with `flash()` for success/error feedback (Flask's session-based
flash, unrelated to the `/kiosk`↔`/` display flash).

Notes:
- **Scan Card** (`_rfid_register.html`, included by the Teachers/Students
  list pages and each teacher's/student's own page) arms
  `admin_rfid_register_start()` so the next `/kiosk` tap (real reader or
  the simulated page) is captured instead of handled as attendance. With
  `data-user-id` (a person's own page) the tag is written to their row
  immediately; without one (the Add forms) it's only captured and dropped
  into the form's hidden `rfid_tag` field. Times out after 30 seconds.
- The class assign and delete routes accept an optional hidden
  `teacher_context` field (the teacher_id); when present they redirect back
  to that teacher's detail page instead of `/admin`, which is how the
  teacher-page forms stay on the teacher page after a save. It's validated
  as an int and only ever used to build a `url_for(...)` call, so it can't
  be abused as an open redirect.
- Deleting a class dissolves *everything* tied to it — every student's
  `enrollments` row for it (they're simply no longer in that class,
  same as if manually unenrolled, except in bulk) and its `attendance`
  history, deleted along with the class row itself rather than getting
  blocked by foreign keys. Its teacher assignment is dissolved too,
  trivially — the class row (including `teacher_id`) no longer exists —
  so no separate cleanup step is needed for that part. There's a
  `confirm()` prompt in the UI naming the attendance/enrollment loss
  before the request is ever sent. Deleting a teacher, by contrast, is
  still blocked while they have any class assigned to them (reassign or
  delete those classes first — deleting a *class* is how you'd clear that
  block, not deleting the teacher directly). Deleting a student clears
  their `enrollments` freely (not treated as a record worth blocking on)
  but is still blocked by their `attendance` history, same as before
  enrollment existed — unenroll doesn't touch attendance, but deleting the
  student still requires that history to be gone first.
- A class with `start_time`/`end_time` still `NULL` (freshly added, before
  an admin has set its room/time) is invisible to `get_teacher_class_today()`
  and won't show up on the display or dashboard as a session — the
  "Not scheduled" pill on its card (teacher page) is the signal to go
  set a time for it. The same rule gates enrollment: it's also excluded
  from the Subject/schedule dropdowns on a student's Edit page until it
  has both times set.
- Both admin pages require an admin login (see "Login system" above) — the
  `/kiosk` RFID-tap page is the one place left with no login of its own
  (see "Known simplifications" below).
- The "Add Teacher" form also collects a login `username` and `password`
  (both required), hashed into `teachers.password_hash` on insert. A
  "Reset Password" form on the teacher's own page (`/admin/teachers/<id>`,
  "Edit" in the Teachers table — the same layout as a student's page:
  Details, Reset Password, then their classes) lets an admin set a
  new password for them at any time without needing the old one;
  `admin_reset_teacher_password()` and (with `teacher_context`)
  `admin_update_teacher()` redirect back to that page.
- Class start/end times on both Assign Class surfaces are 24-hour `HH:MM`
  scroll-wheel pickers (`time_input`), normalized by `normalize_time_24h()` in
  `admin_assign_class()` — see "Conventions" above.
- Both "Add Teacher" and "Add Student" (and the Details form on each
  teacher's/student's own page) also
  collect an optional `phone_number` — unlike `username`/`password`, this
  one is never required and can be cleared, since it's just an SMS
  notification target, not a login credential (see "SMS Notifications"
  above).

## RFID hardware listener (`rfid_listener.py`)

The real RC522 reader pathway — this is "the plan" referenced in "What
this project is" above, now implemented. Runs as its own process on the
Raspberry Pi, **alongside** `python3 app.py` (it only POSTs to the Flask
app; it doesn't start it):

```bash
python3 app.py            # terminal 1 — the Flask app itself
python3 rfid_listener.py  # terminal 2 — the RC522 tap listener
```

- Loops forever, calling `SimpleMFRC522().read_id()` (from the `mfrc522`
  library) to detect a tap — deliberately `read_id()`, not `read()`:
  `read()` also attempts a text-block auth/read on the card, which isn't
  needed for an ID-only tap and can print harmless but confusing "AUTH
  ERROR" messages for tags that don't have that block formatted.
  `read_id()` just blocks until a card is present and returns its unique
  ID, nothing else.
- POSTs that ID with `requests.post("http://127.0.0.1:5000/kiosk",
  data={"rfid_tag": str(card_id)})` — the *exact* same endpoint and form
  field name `/kiosk`'s own simulated tap form already posts to
  (`kiosk()` in `app.py` reads `request.form.get("rfid_tag", ...)`
  regardless of whether the POST came from a real browser form or this
  script), so nothing in `app.py`, `handle_teacher_tap()`, or
  `handle_student_tap()` needed to change for real hardware taps to work
  — a tag unknown to `teachers`/`students` gets the same "Unknown tag: …"
  response either way.
- Debounces after every read with a 2.5-second `time.sleep()` before
  looping back to `read_id()`, so holding one card near the reader too
  long doesn't register as several rapid repeat taps.
- Prints a line to the console for every tap — on a successful POST
  (`[rfid_listener] Tap sent: rfid_tag=... (status 200)`) and on any
  failure, whether the Flask app returned an error status or the request
  itself failed outright (app not running, wrong port, network hiccup —
  caught as `requests.exceptions.RequestException`).
- `Ctrl+C` stops the loop and calls `GPIO.cleanup()` in a `finally` block
  before exiting, releasing the RC522's GPIO pins cleanly.
- Needs `RPi.GPIO` and `mfrc522` on top of `requirements.txt`
  (`pip install RPi.GPIO mfrc522`) — deliberately **not** added to the
  shared `requirements.txt`, since both are Raspberry Pi-specific
  (`RPi.GPIO` talks to the Pi's hardware GPIO registers directly) and
  won't install on a regular dev laptop, which would break `pip install
  -r requirements.txt` for the laptop-first dev workflow described in
  "What this project is."
- `/kiosk`'s own web page (text input + quick-tap buttons) still works
  exactly as before and remains the right tool for local dev on a laptop,
  or as a fallback if the reader/Pi isn't available — `rfid_listener.py`
  is an additional tap source into the same endpoint, not a replacement
  for the page.

## Remote access via ngrok

By default the app only listens on `localhost`, so it's only reachable from
the same machine. For remote demoing/testing from other devices — including
over the public internet, not just the same WiFi network — the app can be
exposed with [ngrok](https://ngrok.com), which is what's currently set up.

- Start the Flask app locally first (`python app.py`, listening on
  `localhost:5000`) — ngrok only forwards traffic to an already-running
  local server, it doesn't start the app itself.
- Then, in a **separate terminal**, run `ngrok http 5000`. This generates a
  temporary public HTTPS URL (something like
  `https://xxxx.ngrok-free.dev`) that tunnels to `localhost:5000`, so
  anyone with that URL can reach the app from anywhere, not just the same
  WiFi network.
- On the free tier, that URL is random and temporary — restarting ngrok
  generates a brand-new URL each time, so there's no stable/permanent link
  to bookmark or hand out unless the ngrok account is upgraded to a paid
  plan.
- The first time anyone visits a given ngrok URL, ngrok's free tier shows
  an interstitial "You are about to visit..." warning page that has to be
  clicked through before reaching the actual app. This is normal ngrok
  behavior, not a RoomSync bug.
- The ngrok link points at the same Flask app, so its routing is unchanged:
  `/` is still the classroom schedule/attendance display (the
  Welcome/attendance state machine meant for the door-mounted screen), not
  a teacher-facing page. `/login` and `/dashboard` are the teacher/admin
  pages — anyone using the ngrok link to demo the login system or the
  teacher dashboard (e.g. from a phone on mobile data) needs to manually
  navigate to `/login`, since `/` is intentionally kept as the display
  homepage rather than redirecting to login.
- This is a lightweight stand-in for a real cloud deployment, chosen given
  the project's prototype scope and timeline — it's meant for occasionally
  demoing or testing remotely (e.g. checking the dashboard from a phone off
  the local WiFi), not for any kind of production or always-on hosting.

## Web Push Notifications

A bonus feature beyond the three core manuscript objectives (the same
category as the teacher dashboard and login system) — desktop/mobile
browser push notifications for teachers and students, without any app to
install. **Requires HTTPS**: browsers only expose `serviceWorker` and
`PushManager` in a "secure context," so this only works over the ngrok
tunnel (see "Remote access via ngrok" above) or a real HTTPS deployment,
never over plain `http://localhost` — `_push_notifications.html`'s setup
script checks for both APIs and silently no-ops if either is missing,
which is exactly what happens on plain HTTP.

**VAPID keys** (`generate_vapid_keys.py`): Web Push requires the server to
identify itself to push services (Google's, Mozilla's, etc.) with a VAPID
key pair. `generate_vapid_keys.py` is a one-time setup script (uses
`py_vapid`, a `pywebpush` dependency) that generates an EC key pair and
prints `VAPID_PRIVATE_KEY`/`VAPID_PUBLIC_KEY` as raw base64url strings —
paste them into the constants near the top of `app.py`. This is a
dev-only shortcut (hardcoding config directly in source), the same as
`app.secret_key` right below it — see "Known simplifications". A third
constant, `VAPID_CLAIMS_SUB`, is just a `mailto:` string the push spec
requires in the signed claims; it's never actually emailed. The public key
is also embedded into `dashboard.html`/`student_dashboard.html` (passed as
`vapid_public_key` from `dashboard()`/`student_dashboard()`) as the
`applicationServerKey` the browser needs to create a subscription.

**`push_subscriptions` table** — see "Database schema" above. One row per
browser/device.

**Subscribing** (`templates/_push_notifications.html`, included at the
bottom of both `dashboard.html` and `student_dashboard.html`): on page
load, registers `static/sw.js` as a service worker, checks
`registration.pushManager.getSubscription()` — if a subscription already
exists, does nothing further (so a page reload doesn't re-prompt or
re-subscribe every time). Otherwise it requests notification permission
(`Notification.requestPermission()`), and if granted, calls
`pushManager.subscribe({userVisibleOnly: true, applicationServerKey:
...})` and POSTs the resulting `PushSubscription.toJSON()` (an `endpoint`
plus `keys.p256dh`/`keys.auth`) to `/api/push_subscribe`
(`api_push_subscribe()` in `app.py`). That route takes the `user_type`/
`user_id` from the *session*, never from the request body — a caller
can't register a subscription on someone else's behalf — and requires
`role` to be `"teacher"` or `"student"` (401 otherwise). Re-subscribing
the same `endpoint` (e.g. the page reloading before `getSubscription()`
would've short-circuited it) is a harmless no-op, caught via the
`endpoint UNIQUE` constraint (`sqlite3.IntegrityError` swallowed
silently).

**Service worker** (`static/sw.js`): served as a plain static file — no
dedicated Flask route, since its default scope (`/static/`) is all it
needs. It only does two things: a `push` listener that parses the
notification payload (`{title, body, url}`, sent as the `data=` JSON
string in `send_push_notification()` below) and calls
`self.registration.showNotification(title, {body, data: {url}})`; and a
`notificationclick` listener that closes the notification and either
focuses an already-open tab at that `url` or opens a new one via
`clients.openWindow(url)` — `url` is `/dashboard` for a teacher
notification or `/student-dashboard` for a student one (`url_for(...)`
picks the right one in `send_push_notification()`, based on `user_type`),
which is how a click ends up on "the relevant dashboard" regardless of
which of the two triggered it.

**Sending** — `send_push_notification(user_type, user_id, title, body)`
in `app.py`: looks up every `push_subscriptions` row for that user, and
calls `pywebpush.webpush()` once per row (per device). Two layers of
error handling around each individual send, so one bad subscription can
never take down whichever request triggered the notification or stop the
rest of that user's devices from being tried: a `WebPushException` with a
404/410 response (the browser/OS reports the subscription as
expired/unsubscribed) deletes that row; anything else — a malformed key
that fails local crypto processing before any request is even sent
(`pywebpush` raises a plain `ValueError` for that, not
`WebPushException`), a DNS/network failure, whatever — is caught and
silently skipped, leaving the row in place to retry next time.

**Notification triggers** — three, wired into the existing state machine.
Each one calls `send_sms_notification()` right alongside
`send_push_notification()` (see "SMS Notifications" below) — same
recipients, same message text, the phone number pulled from whichever
teacher/student row is already being queried for the push call, so
wiring SMS in added no extra queries anywhere:

1. **10 minutes before `start_time`** (`_check_ten_minute_reminders()`,
   called from the top of `advance_state()`, *outside*
   `room_state_lock` since it never touches `room_state` and its push/SMS
   sends shouldn't block the state machine for unrelated requests) —
   scans every assigned, tappable class (`teacher_id` and `start_time`
   both set) system-wide, not just whichever class is currently active on
   the shared display; fires once `reminder_at <= now < start_dt` where
   `reminder_at = start_dt - 10 minutes`. Notifies the assigned teacher
   and every enrolled student: *"Reminder: [Subject] starts in 10 minutes
   at [Room]."* (room falls back to "the classroom" if unset). Dedup is
   the in-memory `_ten_minute_reminders_sent` set of `(class_id,
   "YYYY-MM-DD")` pairs — same lifetime/pattern as `_early_ended_sessions`
   — so it fires once per class per day despite `advance_state()` running
   on essentially every request. The `classes` query here joins in
   `teachers.phone_number`, and the enrolled-students query joins in
   `students.phone_number`.
2. **`attendance_open` begins** (inside `_open_attendance_window()`) —
   notifies every student enrolled in that class: *"Attendance is now
   open for [Subject]."* Only reached when the window actually *opens*
   (a teacher's tap, or the `teacher_early_wait` auto-open) — resuming an
   already-open window (the "No" at `end_early_confirm`, or "Cancel" on
   the summary screens, both of which can land back on `attendance_open`)
   sets the stage directly without calling this function, so those don't
   re-fire it. The enrolled-students query here also joins in
   `students.phone_number`.
3. **A session summary is finalized** (`_notify_session_ended()`, called
   from inside `_reset_to_welcome()`) — notifies the teacher: *"Session
   ended: [present]/[total] present, [late] late for [Subject]."* (counts
   from `get_roster_for_date()`, so late taps aren't counted as present). `_reset_to_welcome()`
   only calls this while the stage being left is `session_summary` or
   `session_summary_edit` (checked against `room_state["stage"]` *before*
   the reset), so this fires for both a normal end-of-window finalization
   and an early-end one confirmed "Yes" — but *not* when
   `_reset_to_welcome()` is called from `teacher_early_confirm`'s "No"
   (declining the early-tap prompt never reached a summary at all, so
   nothing should be reported as "ended"). Unlike the other two,
   `room_state` only ever carries `teacher_id`/`teacher_name` — not
   `phone_number` — so this is the one trigger where fetching it costs one
   small extra query (`SELECT phone_number FROM teachers WHERE
   teacher_id = ?`, by primary key), rather than an existing query just
   growing an extra joined column. The same finalization also pushes
   *"You were marked absent for [Subject] today ([date])."* to every
   enrolled student still `absent` on the final roster (after any
   `session_summary_edit` corrections) — a panel recommendation. This
   one is **Web Push only, no SMS**, by the user's choice.

No background task queue anywhere in this — see "Known simplifications"
for what that costs.

## SMS Notifications

A second bonus notification channel, layered on top of Web Push above —
same trigger points, same recipients, same message text, sent via a free
"REST SMS Gateway" Android app on a spare phone with its own SIM card
(no paid SMS API, no new server-side hardware), added specifically per a
panel recommendation during the mock defense.

**How it works**: the spare phone runs the REST SMS Gateway app, which
exposes a local HTTP GET endpoint —
`http://<phone-ip>:<port>/v1/sms/send/?phone=<number>&message=<text>` —
that sends a real SMS through that phone's own SIM/load when hit. This
only works if the Raspberry Pi and that phone are on the **same local
WiFi network**, since it's a plain local HTTP call, not a public API.

**Config** (`SMS_GATEWAY_IP`/`SMS_GATEWAY_PORT`, in their own `config.py`
— `app.py` just does `from config import SMS_GATEWAY_IP,
SMS_GATEWAY_PORT` near its other imports): the IP/port the REST SMS
Gateway app currently displays on the spare phone's screen. Kept in a
separate file specifically so updating them doesn't mean editing `app.py`
— they go stale whenever that phone reconnects to WiFi (or switches
between home WiFi and its own hotspot) and gets a new IP, so this needs
updating by hand fairly often; there's no auto-discovery. To pick up a
new IP: edit the two lines in `config.py`, then restart `python app.py`
— no other file needs to change. (The VAPID keys, by contrast, are
genuinely one-time values that don't need this same churn, so they stay
inline in `app.py` — see "Known simplifications".)

**`SMS_GATEWAY_IP = "auto"`** (the user's setup for presenting: the Pi
connects to the gateway phone's own hotspot, so the phone *is* the
router). `sms_gateway_ip()` in `app.py` then returns the machine's
default gateway, read fresh on every send by `_default_gateway_ip()`.
On the Pi that comes from `/proc/net/route`; on a Windows dev laptop it
comes from `route print`. That way it survives Android picking a new
hotspot address each time the hotspot starts. If no default route
exists (e.g. hotspot off), the send is skipped with a log line, never an
error. A plain IP in `SMS_GATEWAY_IP` works exactly as before.

**`students.phone_number`/`teachers.phone_number`** — see "Database
schema" above. Nullable, admin-set, optional — the SMS equivalent of a
push subscription; no number set means that person just never gets an
SMS.

**Sending** — `send_sms_notification(phone_number, message)` in `app.py`,
matching `send_push_notification()`'s shape and failure philosophy:
- No-ops immediately if `phone_number` is falsy (`None`/empty) — the SMS
  equivalent of a user having zero `push_subscriptions` rows.
- URL-encodes `message` with `urllib.parse.quote()`, then hits the
  gateway's endpoint with `requests.get(..., timeout=10)`.
- Wrapped in `try`/`except` (`requests.exceptions.RequestException`,
  plus a broader `except Exception` for anything else unexpected — a
  malformed phone number, whatever) that logs the failure and returns
  without raising, so a gateway that's unreachable (phone off, off WiFi,
  wrong IP after a reconnect) never crashes whichever request triggered
  the notification, the same guarantee `send_push_notification()` makes
  for a bad subscription.

**Notification triggers**: the exact same three as Web Push (see above)
— 10 minutes before `start_time`, `attendance_open` beginning, and a
session summary finalizing — each one calling `send_sms_notification()`
right alongside `send_push_notification()`, same recipients and message
text, with the phone number pulled from a row already being queried for
the push call (or, for the session-ended trigger, one small extra
query — see point 3 above).

## Known simplifications / things to revisit later

- `app.secret_key` and the VAPID key pair (`VAPID_PRIVATE_KEY`/
  `VAPID_PUBLIC_KEY`) are hardcoded dev values — fine for a local
  prototype, should be replaced (and moved out of source, e.g. environment
  variables) before any real deployment.
- The Teacher/Student/Admin login (see "Login system" above) is simple
  session-based auth suitable for a capstone prototype: no "forgot
  password"/email-based reset (an admin resets a teacher's or student's
  password directly instead), and no rate limiting or lockout on repeated
  failed login attempts. Fine for a capstone demo; would need both before
  any real deployment.
- Web Push (see "Web Push Notifications" above) sends happen synchronously,
  inline, in whatever request triggers them — there's no background task
  queue. A slow or unreachable push service could add latency to that
  request (a kiosk tap, a display poll, etc.), and two of the three
  trigger call sites (`_open_attendance_window()`, `_reset_to_welcome()`)
  run while `room_state_lock` is held, so a slow push send there
  technically blocks the state machine for other concurrent requests too.
  Acceptable for a low-traffic capstone demo; a real deployment would want
  to hand these off to a background worker instead.
- SMS (see "SMS Notifications" above) shares Web Push's simplifications
  and adds its own: `SMS_GATEWAY_IP`/`SMS_GATEWAY_PORT` live in
  `config.py` rather than inline in `app.py` (unlike the VAPID keys and
  `app.secret_key`) precisely *because* this pair actively **goes stale**
  whenever the spare phone reconnects to WiFi (or switches to/from its own
  hotspot) and gets a new IP, silently breaking SMS delivery until someone
  notices and updates `config.py` by hand and restarts `python app.py` (a
  static/reserved IP for that phone on the router would fix the
  root cause, but isn't set up). It's still config committed in plain text
  in the repo, not pulled from the environment or a secrets store — fine
  for a local prototype on a phone that's not a secret, but the same
  "should be replaced before any real deployment" caveat as the VAPID keys
  applies if this ever needs to be kept private. No retry logic and no
  delivery confirmation — a
  `send_sms_notification()` call either gets back whatever the gateway
  app returns (not necessarily proof the SMS was actually sent by the
  carrier, just that the phone accepted the request) or fails silently,
  logged but not surfaced to any teacher/student/admin UI. Requires the
  Pi and the gateway phone on the same local WiFi network — there's no
  path for this to work remotely (e.g. over the ngrok tunnel) the way the
  rest of the app can. Uses no paid API — just the gateway phone's own
  SIM card/load — which is also why there's no usage cap or rate limiting
  on top of what that SIM naturally has.
- Every class meets every single day once its time is set — there's no way
  to schedule a class for only some days of the week, or to add a
  holiday/no-class override, or to handle a class whose time spans
  midnight. Attendance windows and "current class" detection are purely
  wall-clock-time-of-day based.
- `/kiosk` still has no login or auth of its own — anyone who can reach it
  (its web page, or a raw POST like `rfid_listener.py` sends) can tap in
  as any known tag. Fine for a capstone demo/prototype, where reaching it
  at all means being physically at the reader or on the same machine;
  would need real access control before any real deployment.
- RC522 reader integration (via SPI on the Raspberry Pi 4) is done — see
  "RFID hardware listener" above. **Boot-to-kiosk** is set up by running
  `bash pi/setup_autostart.sh` once on the Pi (`--remove` undoes it). It
  installs systemd services `roomsync` (`app.py`) and `roomsync-rfid`
  (`rfid_listener.py`, with `gpio`/`spi` groups), both `Restart=always`.
  It also adds an XDG autostart entry
  (`~/.config/autostart/roomsync-kiosk.desktop`) running `pi/kiosk.sh`,
  which waits for the app and opens Chromium with `--kiosk
  --password-store=basic` (the keyring prompt once left Chromium in a
  reload loop on this Pi). Finally it turns on desktop auto-login and
  turns off screen blanking via `raspi-config nonint`. Once installed,
  restart with `sudo systemctl restart roomsync roomsync-rfid` after a
  `git pull` or a `config.py` change, and read logs with `journalctl -u
  roomsync -f`. Running `python3 app.py` by hand at the same time clashes
  on port 5000. ngrok is not autostarted. `.gitattributes` forces LF for
  `*.sh`.
- The display state machine (`room_state` in `app.py`) is a single
  in-memory dict guarded by a lock — it assumes one room/one process, and
  resets to `welcome` if the Flask process restarts. Fine for the current
  single-room prototype; would need per-room state (and probably a real
  store instead of an in-memory dict) to support multiple rooms/screens.
